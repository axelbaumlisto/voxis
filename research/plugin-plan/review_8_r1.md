## Findings

### F1 — HIGH — `ios/Sources/AudioCapture.swift` (no observer for `AVAudioEngineConfigurationChange`; `emitLevelTick` :390) — a stalled engine keeps ticking `rms: 0` forever (the exact failure desktop review-fix M2 closed)
**What:** `AVAudioEngine` stops itself (and uninitializes) whenever the input hardware's sample rate or channel count changes — Apple's documented behaviour for `AVAudioEngineConfigurationChangeNotification`. The common real-world trigger during dictation is AirPods/BT headset connecting or a wired mic being plugged in *mid-recording* (`.newDeviceAvailable`, 48 kHz built-in → 16/24 kHz HFP). The code only reacts to `.oldDeviceUnavailable` (:487) and `interruptionNotification`. After a config change: tap stops firing, `levelTimer` keeps ticking `peak: 0`, the RMS≈0 heuristic flips `muted: true` after 500 ms, the guard treats it as silence, and `stop()` returns a **fabricated success** with only the pre-change samples (or the 75 s silence timeout discards everything the user said). This is precisely the "ticks flowing with `rms: 0.0` forever" case desktop's M2 fixed by flipping `stage` to `Failed`.
**Fix (small):** in `installInterruptionObservers` also observe `.AVAudioEngineConfigurationChange` with `object: engine` → `queue.async { failWithInterruption(reason: "engine configuration change") }`. Belt-and-braces (2 lines): at the top of `emitLevelTick`, `if !engine.isRunning { failWithInterruption(reason: "engine stopped"); return }` — this also covers any future stop path nobody observed. Add both to the T8.5 checklist (item A below).

### F2 — MEDIUM — `src/mobile.rs:87` `run_blocking_ipc` — the `spawn_blocking` wrapper does not deliver the property it claims
**What:** `run_blocking_ipc` spawns `run_mobile_plugin` onto Tokio's blocking pool and then the **caller blocks on `rx.recv()`**. The caller is `commands.rs::do_start` (`async fn`, line 51) / `pipeline.rs:224` finalize — Tokio async workers. So the async worker is pinned for the whole round-trip anyway; the wrapper only adds a thread hop and a second mpsc. The module doc even admits it ("the calling thread still waits either way"). Task text `[R1-iOS C5]` intends `spawn_blocking(...).await` at the async call site. The one call that can actually pin a worker for a long time is `startCapture` during the first-run permission prompt (seconds to minutes while the user reads the dialog). `IosKeychainSecretStore` (:286) inconsistently calls `run_mobile_plugin` directly — which is the honest version.
**Fix (pick one, both small):** (a) delete `run_blocking_ipc`, call `run_mobile_plugin` directly in `IosCapture` (as naked and `IosKeychainSecretStore` already do), and rewrite the module doc to say plainly "blocks the calling thread for one Swift round-trip; Swift handlers return immediately so this is bounded by the operation itself" — or (b) keep the trait sync but in `commands.rs::do_start` wrap `state.capture.start(&path, cap_samples)` in `tauri::async_runtime::spawn_blocking(..).await` (desktop `CpalCapture::stop` joins two threads and would benefit too). I'd take (a) now + note (b) as follow-up; either way the current doc comment must stop claiming a benefit that isn't there.

### F3 — MEDIUM — `docs/PLUGIN_IOS_HOST.md:23` — factually wrong claim about a missing `NSMicrophoneUsageDescription`
**What:** The doc says a missing key yields "a silent `PermissionDenied` (never a device-level crash)". On iOS, accessing privacy-sensitive resources without the usage-description key **terminates the app** (TCC crash: "This app has crashed because it attempted to access privacy-sensitive data without a usage description"). A host author following this doc would be told the wrong failure mode for the single most common integration mistake.
**Fix:** rewrite that cell: "iOS terminates the app at the first `requestRecordPermission`/`AVAudioEngine.start` if this key is missing — it is not a soft denial." Add "run once with the key deliberately removed and confirm the crash log" to the T8.5 checklist (item F below).

### F4 — LOW — `AudioCapture.swift:281-289` engine-start failure branch leaks the interruption/route observers
`installInterruptionObservers()` is called before `engine.start()`; the `catch` removes the tap and clears `running` but does not call `removeInterruptionObservers()`. Each failed start leaves two registrations behind (next start overwrites the references → they can never be removed; `failWithInterruption`'s `wasRunning` guard makes duplicates functionally harmless, but it is a leak). **Fix:** add `removeInterruptionObservers()` to the `catch` block (or move `installInterruptionObservers()` after a successful `engine.start()`).

### F5 — LOW — `src/mobile.rs:203` one `Channel::new` per `start()` leaks into Tauri's global `CHANNELS` map
On mobile, `Channel::new_with_id` calls `plugin::mobile::register_channel` and `Channel::new` passes `on_drop: None` — the entry is never removed (Tauri design). Each session leaks one `Arc<ChannelInner>` + a `watch::Sender` clone. Small, but unbounded over the app lifetime and trivially avoidable: create the `Channel` once in `IosCapture::new` (it already owns `level_tx`), store it, and pass `self.on_level.clone()` in `StartCaptureArgs` (Channel is `Clone`). Simpler code, no leak.

## Minors
- `AudioCapture.swift:293/:567` `UIImpactFeedbackGenerator(...).impactOccurred()` is called on the capture queue; UIKit feedback generators should be driven from the main thread (Main Thread Checker will flag it). Wrap in `DispatchQueue.main.async`. (No-op on iPad anyway.)
- `AudioCapture.swift:390-414` first two ticks: if no tap buffer has arrived yet (slow BT route start, engine priming), both windows read 0 → spurious `muted: true` at t=500 ms; guard-harmless but the overlay would flash "Muted". Gate the heuristic on "at least one tap buffer observed this session" (a `sawAudio` flag set in `processTap`).
- `WavWriter.swift:61` allocates a `Data` per sample (1.9 M allocations for a 120 s Hold cap) — likely a few hundred ms on `stop()`. Encode into a `[Int16]`/`UnsafeMutableBufferPointer` and append once. Also NaN divergence: Swift `min/max` pass NaN through to `32767`, Rust's `clamp` + `as i16` gives `0` — irrelevant unless the converter emits NaN, but cheap to guard (`sample.isNaN ? 0 : …`).
- `WavWriter.selfCheck()` only checks size + three magics; add the `fmt` fields (offsets 20–35) and `[1.0, -1.0, 0.5]` → `[32767, -32767, 16383]` so a conversion regression fails loud too (the Rust test at `audio_wav.rs:187-284` does exactly this).
- `VoxisCaptureError.interrupted(_ reason:)` is called with the constant `"interrupted"` from both sites — pass distinct reasons (`"session interruption"`, `"route: old device unavailable"`, and F1's `"engine configuration change"`) so T8.5 logs tell them apart.
- `AVAudioSession.mediaServicesWereResetNotification` is not observed; after a media-server reset the `let engine` instance is dead and every later `start()` fails. Rare; at least add to the checklist. (Would need `engine` to become `var` and be rebuilt.)
- No `.endOfStream` flush of the converter on `stop()` — loses the SRC tail (< 10 ms). Negligible; note only.
- `src/mobile.rs:69` `#[cfg(target_os = "ios")]` on `ios_plugin_binding!` is redundant inside an already-gated module (harmless, naked does the same).
- `lib.rs::init_ios_with` repeats `build`'s setup tail (`config_dir`/`cache_dir`/`TauriEventSink`/`sweep`/`manage`); a `finish_setup(app, secrets, capture, hotkey)` helper would remove the duplication. Not blocking.
- `outputFormat: AVAudioFormat!` could be a plain optional (it is only ever read via `guard let`).
- Keychain `WhenUnlockedThisDeviceOnly` is what the step mandates, but note for Task 9a/9b: a background/locked-screen finalize will fail `secrets.get(api_key)` with `errSecInteractionNotAllowed`. Not a Task 8 defect — record it in the doc's `[T9a]` section.
