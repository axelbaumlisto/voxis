## Findings

### H1 — `LevelSample.peak` is always ~0.0 → silence guard auto-stops every real-mic recording
- **File:** `crates/tauri-plugin-voxis/src/desktop.rs` level thread (`start()`, the `LevelSample { rms: window_peak.take_peak(), peak: window_peak.take_peak(), .. }` block, ~line 195–200 of the new file).
- **What:** `take_peak()` swaps the accumulator to 0 and is called **twice**; the second call (assigned to `peak`) returns 0.0 unless a cpal callback lands in the few ns between the two calls.
- **Why it matters:** `guard_adapter.rs:46` feeds `sample.peak` (not `rms`) into `guard_step` as the silence metric. With `peak == 0.0` on every 250 ms tick, the silence timeout fires on *every* CpalCapture session regardless of speech — the manual acceptance "hold alt_r → запись → текст" will produce a `Silence` guard outcome after `silence_timeout_ms`. The `voxis://level` event's `peak` is also 0 for the overlay.
- **Fix:** `let peak = window_peak.take_peak(); LevelSample { rms: peak, peak, .. }` (rms and peak carry the same "window peak RMS" metric here, which matches desktop `take_rms_peak`). Factor the sample construction into a pure fn in `desktop/pure.rs` and add a test asserting `peak == rms != 0` after `observe(0.5)`.

### H2 — Hotkey press/release edges dispatched as independent `spawn`s → quick tap leaves recording running (stuck-recording class)
- **File:** `crates/tauri-plugin-voxis/src/lib.rs` `PluginHotkeySink::{on_pressed,on_released}`.
- **What:** Each edge is `tauri::async_runtime::spawn`ed separately with no ordering. `on_pressed` stores `active_session = Some(id)` only *after* `do_start(..).await` completes (rec-file creation, `capture.start`, pipeline spawn). A short Hold-tap produces a release task that runs concurrently, reads `active_session == None`, and does nothing. The start then completes and the session stays `Recording` until self-cap/silence (and with H1, silence). Toggle mode has the analogous double-tap race.
- **Why:** Desktop Voxis routes press/release through Tauri events consumed sequentially (`src-tauri/src/hotkey/mod.rs` `TauriHotkeySink` → orchestrator); this adapter dropped that ordering. Non-blocking on the rdev thread is correctly preserved (good) — but ordering must be too.
- **Fix (KISS):** make `active_session` a `tokio::sync::Mutex<Option<SessionId>>` and hold it across the whole start/stop `await` in both handlers (release then waits for the in-flight start, sees the id, stops it). Alternative: a single `mpsc` edge queue drained by one long-lived task. Add a unit test on the serialisation logic (the existing `fake_sink_drives_hold_start_and_toggle_flip` test re-implements the callback in the test body and never touches `PluginHotkeySink`, so this race is untested).

### M1 — `cap_samples` unit mismatch: self-cap fires ~3× too early at 48 kHz
- **Files:** `crates/tauri-plugin-voxis/src/commands.rs:48-49` computes `native_cap_samples(max_recording_ms, TRANSCRIPTION_SAMPLE_RATE /*16 kHz*/)`; `desktop.rs::build_stream` → `accumulate_capped(&mut buffer, &mono, max)` compares that 16 kHz count against the **native-rate** buffer.
- **Why:** Desktop Voxis (`src-tauri/src/orchestrator/recording.rs:520-527`) passes `recorder.sample_rate()` (native). Here a 60 s cap becomes 20 s on a 48 kHz mic, ~21.8 s at 44.1 kHz. The trait caller cannot know the native rate up front, so the backend must scale.
- **Fix:** in `run_capture_thread` after `native_rate` is known: `max_samples.store((cap_16k as u64 * native_rate as u64 / TRANSCRIPTION_SAMPLE_RATE as u64) as usize)` (saturating; keep `usize::MAX` passthrough). Document in `capture.rs` that `cap_samples` is expressed at 16 kHz. Pure helper + test.

### M2 — Stream error / device unplug is invisible: ticks keep coming, `stop()` returns Ok
- **File:** `desktop.rs::build_stream` `err_fn = |err| tracing::error!(..)`.
- **What:** On `cpal` stream error the closure only logs. `stream_running` stays `true`, the level thread keeps publishing `rms 0.0` samples, so the `[R1-Arch S3]` liveness (`StreamDied`) never fires and `stop()` returns `Ok(CaptureStats)` with a truncated WAV and no error. The module doc ("makes a stream death visible as ticks stopping") is therefore false. Desktop `stream.rs:262` also only `eprintln!`s, so this is *parity*, but the plugin's contract explicitly makes level ticks the liveness signal.
- **Fix:** capture `stream_running` + `last_error` in `err_fn`; on error `record_error(..)` and `stream_running.store(false)` → level thread exits (liveness fires) and the next `stop()` returns `Err(Backend(cause))`. Two lines.

### M3 — Level thread's fixed 250 ms grace races slow device open → healthy session reported dead
- **File:** `desktop.rs` level thread: `std::thread::sleep(LEVEL_INTERVAL); loop { if !stream_running { return; } .. }`.
- **What:** If `default_host()`/`default_input_config()`/`build_input_stream` take > 250 ms (first-run TCC microphone prompt, Bluetooth/aggregate devices, CoreAudio warm-up are all routinely slower), the level thread sees `stream_running == false`, exits, and no tick ever arrives → liveness declares `StreamDied` on a stream that is actually fine; `stop()` returns Ok so nothing explains it.
- **Fix:** replace the sleep with an explicit startup handshake (e.g. `mpsc::Receiver<Result<(),()>>` or a `Condvar`/`AtomicU8 {Starting,Running,Failed}`): loop while state == Starting, exit on Failed, tick on Running. Keeps the "never came up → no ticks" property without the timing assumption.

- Audio callback allocates a `Vec<f32>` (`mono`) per buffer and takes a `std::Mutex` on the realtime thread — same as desktop's shape; contention-free since `stop()` only locks after joining. Could push directly into the buffer to avoid the temp Vec; not blocking.
