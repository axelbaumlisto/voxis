## Findings

1. **[Moderate, not blocking 6b] `crates/voxis-core/src/config/mod.rs` (`AppConfig::min_recording_ms`) vs `crates/voxis-core/src/storage/config_sqlite.rs` `load()`/`save()`** — same bug class as the `api_url_override` bug this step fixes. `min_recording_ms` is a real `AppConfig` field (config/mod.rs, struct field list, `#[serde(default = "default_min_recording_ms")]`) but neither `ConfigSqliteStorage::load()` nor `::save()` ever reads/writes a `min_recording_ms` key (grep for `min_recording_ms` in `config_sqlite.rs` returns nothing). Every load silently resets it to `AppConfig::default()`'s value (300ms) regardless of what the user configured in Settings, exactly the same silent-revert-on-restart shape as the bug this step fixes for `api_url_override`. This is **pre-existing** and **out of scope** for Task 6b's approved single-field fix, and does not affect gate 7 / the profile-import path (the profile layer reads `min_recording_ms` from the live `AppConfig` in memory, and the data-gate golden fixture already reflects the pre-existing (broken) always-300 behaviour, so nothing here regresses). Recommend the orchestrator file a fast, narrowly-scoped follow-up task mirroring the `api_url_override` fix (identical `get_typed`/`set` pair, no convention change needed). Not a reason to reject 6b itself — the supervisor-approved fix was scoped to `api_url_override` only, and widening it here would require its own test/verification pass. I checked all other `AppConfig` fields against both `load()`/`save()`; every other field (including the new `audio_device` machinery, `vad`, `overlay`, `llm`, `dictionary`, `paste_shortcuts`, etc.) has a matching read/write pair. `min_recording_ms` is the only field with this gap.

2. **[Minor] `guest-js/src/types/contract.ts` `ImportSummary.source` union is unvalidated at runtime.** Narrowing `source: string` → `"desktop" | "qr" | "passphrase"` is accurate (the Rust side only ever constructs `ImportSummary` with one of those three literals — confirmed via grep in `profile_source.rs`/`models.rs`), but unlike `ProfileConfigDto` (which goes through `parseProfileConfig`'s runtime `expectString`/`expectOptionalString` validators), `ImportSummary` is never runtime-parsed — `client.ts` does a bare `invoke<ImportSummary>(...)` cast. The union is documentation-only, not enforced. Pre-existing pattern (not introduced by this diff), and low risk since the Rust source is fully in this codebase's control. No action required, just noting it isn't the same guarantee `ProfileConfigDto`'s fields get.
