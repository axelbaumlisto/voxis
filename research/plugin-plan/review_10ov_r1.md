VERDICT: APPROVE

## Findings

None blocking. Two minor test-coverage gaps noted below (see Minors) — neither is a correctness defect in the shipped code.

## Checked and OK

1. **DRY / single code path.** `wireClientEvents` (client mode) no longer contains any indicator/theme/session-clearing logic itself — it only subscribes and forwards each payload straight into the new public `applyState`/`applyLevel`/`applyResult` methods (`void client.onState((state) => this.applyState(state))`, etc.). All the actual behaviour (indicator update, `themeBridge.setFromLevel`, the idle-clears-session guard, result-clears-session) lives exactly once in the three `apply*` methods. Host mode calls the same three methods directly. No duplicated logic between drivers.

2. **Host mode never touches a client.**
   - `mountOverlay`: `client: driver === "host" ? options.client : options.client ?? createClient()` — `createClient()` is only reachable on the `"client"` branch of the ternary; in host mode a passed-in client is stored (unused) but `createClient()` itself is never invoked. Confirmed by reading the source, not just inferred from tests.
   - `wireClientEvents` early-returns `if (config.driver !== "client") return;` before ever reading `config.client` — no `onState`/`onLevel`/`onResult` subscription in host mode. Test explicitly asserts `client.onState/.onLevel/.onResult` were never called even when a client is passed alongside `driver: "host"`.
   - `wirePointerHandling` dispatches to `wirePointerHandlingHostDriven()` for host mode, which only dispatches `voxis-overlay-press` and never calls `startActive`/`stopActive`. `startActive`/`stopActive` additionally self-guard (`this.config.driver === "host" || !this.config.client`) as defense-in-depth since the theme's own `cancel` action (`mountTheme`) also routes through `stopActive`.
   - Window `blur`: the `window.addEventListener("blur", this.handleWindowBlur)` call sits after the client-mode branch in `wirePointerHandling` (host mode returns before reaching it), so no listener is ever added in host mode; test spies on `addEventListener` and confirms no `"blur"` registration, and confirms dispatching `blur` doesn't throw.
   - `disconnectedCallback` unconditionally calls `window.removeEventListener("blur", ...)`, `unlistenState?.()`, etc. — all safe no-ops in host mode since nothing was registered/assigned. Test compares the set of added window listener types against removed ones after `el.remove()` and finds no leftover (`resize`/`orientationchange`, shared with client mode, are added+removed symmetrically; `blur` is in neither set).
   - `configure()` itself does no additional validation beyond storing the config object — consistent with the rest of the API (`mode`/`theme`/`storageKey` aren't runtime-validated either), so no regression in validation rigor.

3. **`applyResult` parity with client-mode behaviour.** The three `apply*` methods are a direct extraction of the pre-existing `wireClientEvents` callback bodies with no logic changes (confirmed against the diff: the `[fixed per REJECT-FIX L3]` idle/result session-clearing comments are carried over verbatim). Since client mode now calls these same methods rather than a parallel copy, there is no way for `applyResult`/`applyState`/`applyLevel` to diverge from "old" client behaviour — they *are* the old client behaviour. `applyState` still updates `currentState`, `updateIndicator()`, and `themeBridge.setFromLevel(pluginStateToThemeMode(state), 0, false)`, and clears the active session on idle; `applyLevel` still uses `pluginStateToThemeMode(this.currentState)` (correctly depends on state already applied via `applyState`, same ordering assumption as before); `applyResult` clears the active session. No dropped state.

4. **Docs example correctness.** `docs/THEMES.md` appendix example (`mountOverlay(document.body, { driver: "host" })` + `client.onState((s) => el.applyState(s))` / `applyLevel` / `applyResult`) matches the real public API exactly — `applyState`/`applyLevel`/`applyResult` are indeed public instance methods on `VoxisOverlayElement`, and `driver: "host"` is a real `MountOverlayOptions` field. Accurate.

5. **No gold-plating found.** The extra ternary allowing a client to be passed alongside `driver: "host"` (stored but unused) is minimal, explicitly tested, and matches a real usage mistake a host might make; not scope creep. Comment volume is consistent with this file's existing dense-commenting style (e.g., pre-existing `[fixed per REJECT-FIX L3]` annotations).

## Minors

- **`createClient` non-invocation isn't asserted by a spy/module mock** — it's only inferred (correctly, by reading the ternary) rather than proven by a test that mocks `./client`'s `createClient` export and asserts it wasn't called. The existing test ("mounts without a client... even if passed anyway") only proves no *subscription* happens on an injected mock client, and no-throw when no client is given at all; it wouldn't catch a hypothetical future regression where `createClient()` is called but its result silently discarded. Low risk given the ternary is trivial to eyeball, but a `vi.mock("../src/client")` spy would close the gap definitively.
- **`applyLevel`/`applyResult` cross-driver equivalence is only "does not throw," not value-parity.** The `it.each(["client","host"])` parametrized test only covers `applyState`'s indicator/theme-mode text; the host-mode `applyLevel`/`applyResult` test doesn't assert dot/theme state changes the way the `applyState` one does. Since all three methods are the *same* function regardless of driver (per Finding 1), this is low-risk, but the parametrization pattern established for `applyState` isn't extended to the other two, so a future edit that special-cased one driver inside `applyLevel`/`applyResult` wouldn't be caught by a cross-driver assertion.
