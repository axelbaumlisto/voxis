## Findings

1. **[blocker] The hold-to-talk chip never calls `setPointerCapture`, so a release with the pointer dragged off the button can leave a stuck recording — exactly the failure mode the code's own doc comments claim to prevent.**
   `src/components/KeyPanel.tsx` (new `keypanel-voxis-chip` button):
   ```
   onPointerDown={() => voxisChip.handlePointerDown()}
   onPointerUp={() => voxisChip.handlePointerUp()}
   onPointerCancel={() => voxisChip.handlePointerCancel()}
   onLostPointerCapture={() => voxisChip.handleLostPointerCapture()}
   ```
   None of these handlers receives the DOM event, and nothing calls `e.currentTarget.setPointerCapture(e.pointerId)` on `pointerdown`. Without explicit pointer capture, once the pointer (mouse/touch/pen) moves off the button element while held down, a subsequent `pointerup` fires on whatever element is now under the pointer — **not** on the chip — so `voxisChip.handlePointerUp()` is never called and `onHoldStop`/`stopActive` never fires. `pointercancel`/`lostpointercapture` also won't fire in this scenario because no capture was ever established to lose. The only remaining safety net is the `window` `blur` listener, which only helps for alt-tab/app-switch, not for "pressed the chip, dragged off it, released while the app stays focused" — a completely ordinary touch/mouse gesture on a small toolbar button.
   This is not a hypothetical: naked's own codebase has the identical pattern, solved the identical way, in at least five other places — `PaneDividers.tsx:107,499`, `QuickSwitcher.tsx:216`, `PaneLayout.tsx:920`, `useSheetDismissDrag.ts:113`, `useRoomPointerDrag.ts:603` all call `setPointerCapture` on `pointerdown` for exactly this reason (to keep receiving `pointerup`/`pointercancel` for a pointer that leaves the element). The new chip is the one hold/press gesture in this diff that omits it.
   The new test file (`KeyPanel.voxis.test.tsx`) does not catch this because every test fires `pointerDown`/`pointerUp`/`pointerCancel`/`lostPointerCapture` directly at the *same* chip element (`fireEvent.pointerUp(chip)`), which trivially "works" regardless of whether capture was set — it never simulates the pointer leaving the element before release, so the gap is invisible to this suite.
   Fix: in `onPointerDown`, call `e.currentTarget.setPointerCapture(e.pointerId)` (swallow if it throws for a stale/unknown pointer id, same as `useSheetDismissDrag.ts:113-118`) before calling `voxisChip.handlePointerDown()`. This is a small, mechanical fix consistent with the codebase's own established convention — recommend REJECT-FIX rather than REJECT-REDO.

2. **[minor] `voxisOverlayCspGate.test.ts` has no negative control.**
   All five assertions are "grep the real vendored `dist/*.js` and expect the pattern to be absent." There's no fixture test proving the same regex/`includes` check actually *fails* when the pattern IS present (e.g., a small in-test string containing `eval(x)` run through the same matcher). The regexes themselves are reasonable and mirror the plugin's own `guest-js/__tests__/csp-bundle.test.ts` approach (per the test's doc comment), so this is not a blocker, but a future accidental change to the matching logic (e.g. an errant `!` flip) would not be caught by this suite. Not required to fix now.
