# EXECUTABILITY / ORDERING review R2 — tauri-plugin-voxis plan v2.1
## Verdict: GO-WITH-CHANGES — DAG is mostly sound and unusually well-evidenced, but one real missing gate (T11b→T9a) and one unresolved tooling gap (`e2e:host-min` has no defined script/workspace) must be fixed before `/ado` runs it.

## Strategic findings (max 6)

**F1 [P1] Missing Depends edge: Task 11b needs Task 9a, but Depends: only lists Task 11.**
Quote: "Task 11b … **Depends:** Task 11 (фоновой вариант `AudioRecordingIntent & LiveActivityIntent`, iOS 18 — только после Task 9a: без Live Activity в `perform()` «the audio recording stops»)".
Evidence: the actual `Depends:` line contains only `Task 11`; the Task 9a requirement is buried in a parenthetical, not a second Depends entry. Task 9a's own Depends is `Task 8.5`; Task 11's is `Task 8.5, Task 10`. Neither orders 9a before 11 or vice versa, so a gated executor parsing `Depends:` tokens will schedule 11b as soon as 11 is green — concurrently with, or before, 9a.
Impact: 11b's background-intent path can be implemented/merged before the Live-Activity plumbing it depends on exists, silently producing a broken "recording stops" background flow that the plan explicitly warns about.
Fix: change Task 11b's line to `**Depends:** Task 11, Task 9a` (two tokens), keep the explanatory parenthetical as prose only.

**F2 [P1] `bun run e2e:host-min` is invoked by three tasks but never defined anywhere in the DAG.**
Quote: Task 3.5 Verify: "`cargo test -p tauri-plugin-voxis && bun run test:run && bun run e2e:host-min` локально и в CI"; also Task 6 Verify (`bun run e2e:host-min -- --grep profile`) and Task 11 docs reference the same command.
Evidence: root `/Users/shamash/work/voxis/package.json` has no `workspaces` field and no `e2e:*` script (only `dev, harness, build, build:themes, preview, tauri, test, test:run, test:coverage, test:e2e, test:all, test:rust, lint`). No task's `Files:` list touches root `package.json`, and `crates/tauri-plugin-voxis/examples/host-min/**` (owned by T3.5) is a separate Tauri app whose own `package.json` script would not be reachable via a bare `bun run e2e:host-min` from repo root without either a bun workspaces config or a root-level forwarding script.
Impact: Verify command as written cannot run; T3.5's own CI gate (which blocks T4/T6/T7) would fail for a tooling reason unrelated to the feature.
Fix: add `"workspaces": ["crates/tauri-plugin-voxis/guest-js", ...]` (or an explicit forwarding script `"e2e:host-min": "cd crates/tauri-plugin-voxis/examples/host-min && bun run e2e"`) to Task 3.5's Files/Steps, or state explicitly which directory the command must be run from.

**F3 [P2] Gate 2 ("один контракт — одни фикстуры") claims Task 3's Rust tests and Task 5's vitest consume `contract/fixtures/*.json`, but those fixtures are Files of Task 3.5, which Depends on both Task 3 and Task 5.**
Quote (Гейты §2): "`crates/tauri-plugin-voxis/contract/fixtures/*.json` … читают Rust-тесты плагина, vitest guest-js и позже обёртка naked."
Evidence: Task 3 `Files:` has no `contract/**` entry and its Verify (`cargo test -p tauri-plugin-voxis`) doesn't cite fixtures; Task 5 `Files:` likewise has no `contract/**`. Task 3.5 (`Depends: Task 3, Task 5`) is the only task whose Files include `contract/fixtures/*.json`, and its own Acceptance says the fixtures are "парсятся Rust-тестами и vitest (тест-снапшот с обеих сторон)" — i.e. it's T3.5's own tests, not T3/T5's.
Impact: read literally, the consistency gate describes a forward reference (T3/T5 can't consume files that don't exist until the task that depends on them). Low risk since the concrete task Acceptance is self-consistent, but it will confuse whoever enforces Gate 2 as a standalone checklist.
Fix: reword Gate 2 to "…читаются Rust- и vitest-тестами внутри Task 3.5, и позже обёрткой naked" to match the actual task graph.

**F4 [P1] Task 3 is oversized relative to every other task in Phase 1/2 and mixes at least three independently-testable concerns.**
Evidence: Task 3 `Files:` spans `lib.rs, commands.rs, models.rs, pipeline.rs, capture.rs, desktop.rs, mobile.rs, permissions/**, guest-js/**` and its single Acceptance block enumerates ~12 command/event surfaces plus a test list of 10 distinct scenarios (happy-path, NoSpeech-discard, AlreadyRecording, cancel-during-Transcribing, HTTP-5xx-cleanup, capture-died-silently→Recover, guard-task-killed→self-cap, Hold-lease-loss, SIGKILL-relaunch-rec-empty, consent-gate, secret-store-no-leak). By contrast Task 1 was deliberately split into 1a/1b and Task 9 into 9a/9b for exactly this reason (stated design principle in the plan itself), but Task 3 is not split.
Impact: one worker + one reviewer cannot realistically produce and review this in one pass without exceeding normal task-review bandwidth; also raises the odds that `guest-js/**` (also claimed by Task 5 in full detail) is scaffolded twice.
Fix: split into **Task 3 (skeleton)** — build.rs, permissions autogen, models.rs, command surface, `AudioCapture`/`SecretStore` traits + `MockCapture` — and **Task 3b (pipeline & failure modes)** — pipeline.rs, guard integration, and the 10 edge-case tests. Task 3.5 then depends on 3b instead of 3.

**F5 [P2] Several Verify commands are correctly human-gated in the plan, but this should be stated explicitly for `/ado`.**
Evidence: Task 8 Verify ends with "прогон на реальном iPad"; Task 8.5 is entirely a hardware protocol; Task 9b Verify is "прогон на iPad/iPhone"; Task 11 Verify mixes `docs/IPHONE_STAND.md` + screenshots; Task 11b Verify is "прогон на iPad/iPhone; Settings → Apps → naked → Siri & Search"; Task 7's "ручной прогон QR" is appended to an otherwise scripted Verify line; Gate 6 ("hardware-прогоны A/B/C на MacBook") is a blocking regression gate with no automated command.
Impact: an executor honoring only `Verify:` text will either stall indefinitely waiting for a shell command that never exits cleanly, or (worse) silently mark these green if the human step is skipped.
Fix: prefix each such Verify line with a literal `HUMAN GATE:` token so `/ado` can route it to a human-in-the-loop step instead of attempting automatic execution — mark Tasks 8 (device half), 8.5, 9b, 11 (device half), 11b, and Gate 6 accordingly.

**F6 [P2] Task 5's `bun run harness` Verify collides in name with the pre-existing, differently-scoped root harness.**
Evidence: root `package.json:9` already defines `"harness": "vite"` wired to the existing `harness.html` (confirmed present at repo root, referenced from `vite.config.ts:27`) — this is the **theme-engine** visual harness documented in `docs/THEME_EDITING.md`, unrelated to the plugin's `<voxis-overlay>` web component. Task 5's `Files:` list (guest-js package + its own `__tests__/**`) does not touch `harness.html` or `vite.config.ts` to add an overlay-preview entry.
Impact: running `bun run harness` per Task 5's Verify will open the existing theme-engine harness, not a guest-js overlay preview — the Verify step doesn't test what Task 5 built.
Fix: either add a new root script (`"harness:overlay": "vite --config guest-js.vite.config.ts"`) in Task 5's Files/Steps, or rename to avoid implying reuse of the existing `harness` script.
