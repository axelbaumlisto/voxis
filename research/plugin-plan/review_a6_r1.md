Scope reviewed: `crates/tauri-plugin-voxis/guest-js/{src/overlay.ts,src/themes/registry.ts,src/index.ts,src/theme-bridge.ts,src/types/theme-api.ts,package.json,README.md,__tests__/{overlay,theme-registry}.test.ts,harness/{index.html,themes-grid.html,themes-grid.ts}}`,

## Findings

**Finding 1 (Moderate) — persisted drag position doesn't respect the compact/expanded split, contradicting the documented invariant.**
`overlay.ts` `wireDrag`'s `onDragEnd` callback (~L578, `if (dragged) savePosition(config.storageKey, pos);`) unconditionally persists whatever position the pill was dragged to under `config.storageKey` — the *same* key regardless of `lifecycleState`. If a user drags the pill while `"expanded"` (e.g. mid-recording), the **expanded**-sized dragged position is written to storage. `shrinkToCompact()` does correctly restore the pre-growth in-memory position for the remainder of that page/app session (the `compactPosition` field), so the module doc comment's and README's claim "shrinking back always restores the exact pre-growth position... the compact resting spot never moves underneath a recording session" *is* true within one `connectedCallback` lifetime. But on the **next** mount (`connectedCallback`, e.g. after an app/webview reload), `loadPosition(config.storageKey)` returns that stale expanded-sized/dragged position, and it becomes the new **compact** resting position (merely re-clamped with `COMPACT_SIZE`) — i.e. the documented guarantee silently breaks across a reload. No test exercises a drag-while-expanded followed by unmount+remount with the same `storageKey`, so this ships uncaught. Suggested fix: either skip `savePosition` while `lifecycleState === "expanded"`, or have `shrinkToCompact()` re-save the restored compact position, so the persisted value is always meaningful for the size it'll be reloaded into.

**Finding 2 (Minor) — not all new A6 lifecycle tests are parametrized across both drivers.**
The JUDGE brief and the plan (`task_a6.md` §5, "compact↔expanded по applyState для обоих driver'ов") ask for compact↔expanded coverage on both drivers. Only the core "starts compact... expands... shrinks back" test is `it.each(["client","host"])`-parametrized; the `idleTheme`, `voxis-overlay-resize` event, error-state, and drag-clamp-switch tests exercise `driver: "host"` only. This is a fairly safe gap (both drivers funnel through the same `applyState`/`updateLifecycle` code path, and `wireClientEvents` just forwards client events into `applyState`), but it is a literal shortfall against the stated test plan and would be cheap to close with one more `it.each` pass or a comment explaining why host-only is sufficient.

## Checked OK

- **Lifecycle (JUDGE §1):** `updateLifecycle()` computes `target` purely from `currentState`/`idleTheme` and no-ops when `target === lifecycleState` — confirmed no double mount on `recording → transcribing` (both map to `"expanded"`). `disconnectedCallback` unconditionally calls `unmountThemeInstance()` (idempotent via the `themeMounted` guard) — no leak if unmounted mid-`"expanded"`. `themeBridge` is (re)created synchronously inside `mountThemeInstance()` before `applyState`'s trailing `this.themeBridge?.setFromLevel(...)` call runs, and `applyLevel` also reads the live `this.themeBridge`, so both stay fed while expanded and are safely `undefined`-skipped while compact (no crash, matches "no WebGL loop while idle").
- **Idle visual behaviour change is intentional, not a regression:** pre-A6 the theme was mounted unconditionally at connect regardless of state (even for the four themes with no manifest size — `default`/`handy_pill`/`neon`/`winamp_classic` — which used to render their real idle visuals in the pill at all times). Post-A6 those four themes are also unmounted at idle in favour of the generic ring handle, only showing their real (fallback-sized 64×64) visuals while `"expanded"`. This matches the plan's explicit design (`task_a6.md` §2: "тема НЕ смонтирована" while idle) and is called out in README/THEMES.md — correctly implemented, not an oversight.
- **Geometry (JUDGE §2):** `anchorGrow` computes independently-per-axis nearer-edge growth (`nearerRight`/`nearerBottom` from box center vs. viewport center), verified against all four `anchorGrow` unit tests (top-left/right-edge/bottom-edge/corner). - **Host-driven mode (JUDGE §3):** `applyState` is the single code path both `driver: "client"` (via `wireClientEvents`) and `driver: "host"` (direct call) use — no divergent logic. `dispatchResize()` fires a `CustomEvent("voxis-overlay-resize", {detail:{width,height,state}})` on every `growToExpanded`/`shrinkToCompact` transition (tested for both directions). `el.size`/`el.lifecycle` getters present and public (also exported types). `wirePointerHandlingHostDriven` (unchanged by this diff) still dispatches `"voxis-overlay-press"` on down/up regardless of lifecycle. `wireDrag` still gates entirely on `config.draggable` (unchanged), so `draggable:false` is respected identically in both states.

## Minors

- `applyLifecycleClasses()` is invoked redundantly (once from `updateIndicator()`, again from `growToExpanded`/`shrinkToCompact` inside `updateLifecycle()` when it fires) on every `applyState` call — harmless (idempotent DOM class toggles) but slightly wasteful; not worth blocking on.
- `themes-grid.ts`/`themes-grid.html` compute `rect.left/rect.top` via `getBoundingClientRect()` before the DOM has necessarily laid out the newly-appended `.slot`/`.anchor` nodes in the same synchronous tick — likely fine in practice (screenshot pre-verified as showing correct positions per the task brief) but slightly fragile if grid CSS changes; not reviewed further given the harness screenshot was pre-verified out of band.
- `ManifestSizeFields.entry: string` being required purely to dodge TS2559's weak-type check (per its own doc comment) is a mildly awkward workaround; harmless, well-documented.

## Notes for the naked host

- Listen for `"voxis-overlay-resize"` (`CustomEvent<{width:number; height:number; state:"compact"|"expanded"}>`) on the `<voxis-overlay>` element and resize/reposition whatever container/backdrop the host wraps the pill in — do not poll `el.size`/`el.lifecycle`, they exist for one-off reads (e.g. right after mount) but the event is the source of truth for changes.
- The pill computes its own on-screen position/size, growing/shrinking around whichever screen edge it's already anchored to and clamping itself to the viewport/safe-area — the host does **not** need to reposition the pill itself on resize, only adjust any *other* chrome it draws around/behind the pill (e.g. a highlight ring, a modal backdrop sized to match).
- If the host wants a theme visible even while idle (e.g. a permanent desktop "dock" widget rather than a transient recording indicator), pass `idleTheme: true` to `mountOverlay` — otherwise idle/error always renders as the generic 56×56 ring handle with no mounted theme (see Finding note under "Checked OK" — this is an intentional visual change from pre-`0.2.0`, including for the four themes that have no manifest `overlay_width`/`overlay_height`).
- Be aware of Finding 1 above: if the host's own container reads a persisted/cached size from a previous session for layout purposes (rather than reacting live to `voxis-overlay-resize`), it can transiently disagree with where `<voxis-overlay>` itself renders after a drag-while-expanded followed by a reload, until the first `voxis-overlay-resize`/`applyState` call re-syncs it.

VERDICT: REJECT-FIX
