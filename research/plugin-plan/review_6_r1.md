### F2 — MEDIUM — the three "write-lock contention" tests do not exercise `busy_timeout`
- `sqlite_base.rs` test `open_read_only_succeeds_while_another_connection_holds_a_write_transaction`, `providers/tests_edge_cases.rs::read_only_succeeds_while_a_writer_holds_a_transaction`, `profile_source.rs::import_from_desktop_succeeds_while_desktop_holds_a_write_transaction`.
- Writer does `BEGIN IMMEDIATE` + one small `UPDATE`/`INSERT`. In SQLite's default rollback-journal mode that takes only a **RESERVED** lock, which by design still admits new SHARED readers; PENDING/EXCLUSIVE is acquired only at COMMIT (or on cache spill). So the reader never blocks, `busy_timeout` is never consulted, and the tests would pass verbatim with the `busy_timeout` line deleted. The trailing `assert!(released.load(..))` after `handle.join()` is tautological (join guarantees the thread ran).
- The code itself is right by inspection (`sqlite_base.rs:115`: `conn.busy_timeout(Duration::from_secs(2))`), but the [S7] test claim ("must let the read succeed once the writer commits") is not what's being tested.
- Fix (any one layer suffices, keep the `sqlite_base` one): writer `PRAGMA locking_mode=EXCLUSIVE; BEGIN; UPDATE …` — in exclusive locking mode the first write takes and **holds** EXCLUSIVE, so the reader's SELECT gets SQLITE_BUSY without the timeout and succeeds ~200 ms later with it. Assert `Instant::elapsed() >= ~150 ms` on the reader to prove it actually waited. Drop the tautological `released` assert. Optionally keep one negative control: `Connection::open_with_flags(READ_ONLY)` without `busy_timeout` → `Err` under the same writer.

### F3 — MEDIUM — QR `host`/`token` are interpolated into the URL unvalidated; reqwest client honours system proxy + redirects
- `profile_source.rs` `import_from_qr`: `format!("http://{}:{}/profile?token={}", qr.host, qr.port, qr.token)`. A crafted/photoshopped QR with `host = "evil.example/x?y="` or `"user@10.0.0.1"` or a token containing `#`/`&`/`/` makes the client GET an attacker-chosen http URL. Impact is bounded (AEAD `open` with the user's `code` will fail; only the attacker's own token leaks), but the server side (`profile_share/mod.rs:225,286`) always emits an **IPv4 literal** host and a base64url token, so the client can be strict for free.
- `fetch_sealed_profile`: `reqwest::Client::builder().timeout(..)` — default reqwest follows up to 10 redirects and honours `HTTP_PROXY`/`http_proxy` env; a LAN GET carrying the bearer token would be routed through a configured proxy (leaking the token, and likely failing).
- Fix: `qr.host.parse::<std::net::IpAddr>()` (reject otherwise; brackets for v6 if you accept it), token charset check (base64url: `[A-Za-z0-9_-]`) or build via `reqwest::Url::parse_with_params` (percent-encoding is a no-op for base64url, so still compatible with the server's raw `split('=')` in `server.rs:127-132`); `.no_proxy()` and `.redirect(reqwest::redirect::Policy::none())` on the builder. Add one test: non-IP host → `Err(Profile)` with no network call.
