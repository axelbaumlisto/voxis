# ARCHITECTURE review — tauri-plugin-voxis plan

## Verdict: GO-WITH-CHANGES — the voxis-core split is real for transcription/llm/learning, but `storage/` is not tauri-free as claimed, and the plugin drops two concrete desktop safety nets (native record-length self-cap, stream-died liveness) that the plan should either port or explicitly accept as regressions.

## Strategic findings

**S1 (P1) — `storage/` is not tauri-free; Task 1's "pub-use, nothing else changes" claim is false as written.**
Claim: "Task 1 Acceptance: `voxis-core` не зависит от `tauri`… `voice_lib` использует `voxis_core::*` через `pub use` re-export так, что ни один существующий тест/команда не меняется." Task 1 Step 2 only calls out `config/change_handler.rs` as the tauri-coupled exception that stays in `voice_lib`.
Evidence: `src-tauri/src/storage/mod.rs:40` (`use tauri::{AppHandle, Manager};`), `mod.rs:46` (`get_app_paths(app: &AppHandle)`), `mod.rs:54` (`get_storage_factory(app: &AppHandle)`); `src-tauri/src/storage/paths.rs:9` (`use tauri::AppHandle;`), `paths.rs:151` (`AppPaths::new(_app: &AppHandle)`). These are called from at least six other files: `orchestrator/mod.rs:38`, `setup/mod.rs:38`, `tray/mod.rs:96,138`, `commands/overlay.rs:115`, `orchestrator/post_process.rs:160,235`, `orchestrator/transcription/{debug,pipeline,output}.rs`.
Impact: a literal `pub use voxis_core::{…, storage, …}` cannot compile once `voxis_core` drops tauri as a dependency, because `storage::get_app_paths`/`storage::get_storage_factory`/`AppPaths::new` are tauri-typed functions living in the same module the plan moves wholesale. Either these functions travel with `voxis_core` (violating the "no tauri" acceptance criterion and breaking the iOS cross-build gate) or they must stay behind as a thin voice_lib shim — a step the plan never names, unlike the explicit carve-out it did write for `change_handler.rs`.
Fix: add an explicit Task 1 step: split `storage/{mod.rs,paths.rs}` into a pure part (`AppPaths::from_config_dir`, path builders, traits, sqlite/factory) that moves, and leave `AppPaths::new(&AppHandle)`, `get_app_paths`, `get_storage_factory` as a small tauri-glue shim in `voice_lib::storage` that calls into `voxis_core`. Update Task 1's Files: to include this split explicitly.

**S2 (P1) — No native/self-enforced recording cap ported to the plugin; only the async guard task stops it.**
Desktop has two independent layers: the polling guard (`orchestrator::recording_guard`) *and* an OS/cpal-buffer-level self-cap that fires regardless of guard-task health — `AudioRecorder::set_max_samples`/`cap_hit` (`src-tauri/src/audio/recorder.rs:419-426`), driven from `native_cap_samples` (`orchestrator/recording_guard.rs:318`), wired at `orchestrator/recording.rs:616`. The module doc is explicit about why: "the cpal callback's own `set_max_samples`/`cap_hit` only stops *pushing* into the buffer" as a backstop independent of the guard task (`recording_guard.rs:33-39`).
Evidence in plan: Task 3's acceptance only says "`max_recording_ms` → стоп" at the pipeline/guard level; Task 4's `CpalCapture` and Task 8's Swift `AudioCapture` acceptance criteria never mention a self-cap inside the capture backend itself.
Impact: if the plugin's tokio guard task stalls or is killed (iOS suspending a background executor, a swallowed panic), there is nothing else that stops the capture — unlike desktop, which is capped even if the guard dies.
Fix: require `AudioCapture` implementations (both `CpalCapture` and Swift `AVAudioEngine` capture) to self-cap using the shared `native_cap_samples`-equivalent, not only rely on `pipeline.rs`'s guard.

**S3 (P1) — Plugin has no equivalent of desktop's "stream silently died" liveness detection; this is exactly the loss the task asked to check for.**
Desktop's guard polls `AudioRecorder::is_recording()` every 250 ms and, if it goes false without an explicit stop call, routes to `StopReason::StreamDied` → `StopDecision::Recover` (`orchestrator/recording_guard.rs:441-461`) — this is *generic*: it catches any silent death (panic, device unplug, stream build/play failure after `start()` returned `Ok`), not just a named event.
Plan's Task 8 acceptance only maps a *specific*, explicitly-signaled case (`AVAudioSession` interruption, e.g. a phone call) to "`StreamDied → Recover` (как на desktop)". There is no generic liveness/heartbeat contract in the `AudioCapture` trait (Task 3: `{ start(path); stop() -> Result<CaptureStats>; level_rx }`) that would catch a Swift capture task or cpal stream that dies without emitting an interruption event.
Fix: give `AudioCapture` a liveness signal (e.g., `level_rx` closing/timing out *is* the "died" signal) and make the pipeline treat "no level tick for N polls, capture claims running" the same way desktop treats `is_recording()==false`.

**S4 (P2) — DRY: cpal capture itself is duplicated, not just deferred; only WAV/downsample extraction is loosely "maybe" assigned.**
`voice_lib::audio` already has non-cpal-coupled, movable code — `encoder.rs` (hound-based `downsample`, `samples_to_wav`, `wav_duration_ms`, `TRANSCRIPTION_SAMPLE_RATE`, `src-tauri/src/audio/mod.rs:16`) — but Task 4 step 1 only says "предпочесть перенос в `voxis-core::audio_wav` (**Task 1 может подхватить**)", i.e. no task actually owns doing it. Meanwhile the actual device-selection/stream-building/catch_unwind cpal code (`audio/devices.rs`, `audio/stream.rs`, `audio/recorder.rs`) is *not* proposed for unification at all and will be reimplemented a second time in `tauri-plugin-voxis::desktop.rs` — the plan is honest about deferring that ("Voxis desktop сам как хост своего плагина… убирает дублирование `audio/`" is a Follow-up), but the small, easy win (encoder.rs) is left unowned.
Fix: make Task 1 (not "may") explicitly move `audio::encoder` into `voxis-core::audio_wav`, since it has zero cpal/tauri dependency today and both Task 4 and Task 8 need it.

## Tactical findings

**T1 (P2) — Theme delivery into the plugin's webview is unspecified.** The only existing production path from theme-id → running module goes through a Tauri command (`src/theme-engine/fetchModule.ts` calling `commands.readThemeScript`, backed by `voice_lib`'s file-based `storage::paths::themes_dir`). `loader.ts` (blob/data-URL import) is genuinely portable, but Task 5's Files (`guest-js/src/theme-bridge.ts`) don't name a plugin command or bundling strategy to supply the actual `theme.js` source text to `loadThemeModuleFromSource`. Fix: Task 5 should state explicitly whether it bundles one builtin theme statically (KISS) or adds a plugin command mirroring `read_theme_script`.

**T2 (P2) — `pub(crate)` visibility on the functions Task 1 intends to move.** `stop_decision`, `press_action`, `StopReason`, `StopDecision`, `PressAction`, `stage_to_state` (`orchestrator/recording.rs:66-233`) and the guard's pure functions (`guard_step`, `SilenceWindow`, `native_cap_samples`, `effective_max_recording_ms`) are currently `pub(crate)`/private to `voice_lib`. Moving them cross-crate requires widening visibility to `pub`, which is a real but small mechanical step the plan doesn't mention.

## Depends:/Files: annotation errors

1. **Task 7 is missing `Depends: Task 3.5`.** The "Гейты консистентности" section states plainly: "T3.5 … блокирует T4/T6/T7", but Task 7's block reads `**Depends:** Task 2` only (no Task 3.5). Either add `Task 3.5` to Task 7's Depends (if the gate intent is correct — Task 7 lives in the main voxis repo, not the plugin, so it plausibly doesn't need the plugin tracer bullet), or remove "T7" from the gate sentence. As written, a parallel executor following the per-task `Depends:` line (not the prose gate) would start Task 7 before the gate closes.

2. **Task 1's `Files:` list omits `orchestrator/recording.rs` and `orchestrator/recording_guard.rs`**, even though Task 1 Step 2 explicitly says to move code out of them: "orchestrator::stop_decision + чистая логика guard-окон (`recording_guard` — только функции решения, без tokio-task) в `voxis-core`." `Files:` currently reads only `src-tauri/src/{config,storage,transcription,llm,learning}/` → move plus `lib.rs`/`Cargo.toml`. This under-declares the task's real footprint and risks a parallel worker touching `orchestrator/` in the same window assuming Task 1 doesn't touch it.

## Verified-OK

- `transcription/`, `llm/`, `learning/` have zero `tauri`/`AppHandle`/cpal/rdev/enigo/objc2 references (grep across all three directories: no matches) — genuinely portable as claimed.
- `config/change_handler.rs` is correctly the only tauri-coupled file in `config/` (grep confirms); the rest of `config/` (consts.rs, validation.rs, mod.rs sans change_handler) is clean — matches the plan's explicit carve-out.
- `reqwest` in `src-tauri/Cargo.toml:87` already uses `default-features = false, features = ["json","multipart","rustls-tls"]` — the plan's Task 1 step 3 requirement is already satisfied today, no OpenSSL/iOS conflict to fix.
- `orchestrator::recording_guard::guard_step` (recording_guard.rs:333) and `orchestrator::recording::stop_decision`/`press_action` (recording.rs:158,220) are genuinely pure functions with no `AppHandle`/device dependency — the plan's core design claim ("guard-only functions, no tokio-task, move to core") holds structurally, modulo the visibility/Files gaps noted above.
- `GUARD_POLL_MS = 250` (config/consts.rs:194) matches the plan's stated "250ms Channel of RMS" cadence for the plugin's level events — consistent, not an invented number.
- `src/theme-engine/contract.ts` and `ThemeHost.tsx` are DIP-clean: no `window`/Tauri/`invoke` references anywhere in `theme-engine/` (grep across the whole directory found none outside test/variable names coincidentally containing "window"); `fetchModule`/`onCancel` are injected props, not hard dependencies — the plan's claim that theme-engine mounts into an arbitrary host webview without Tauri-window assumptions holds.
- Clipshot's `gen/apple/project.yml` corroborates Task 9's specific claims: `xcodegen` does own and rewrite `Info.plist`/entitlements from `*.properties` (comments at lines documenting exactly this), the extension needs its own `DEVELOPMENT_TEAM` (`ClipshotShare` target sets it explicitly), and `outputFiles` for `libapp.a` is owned by whichever target links Rust and builds first (here, `ClipshotShare`) — the plan correctly notes Voxis's widget doesn't link Rust and thus avoids this exact hazard.
